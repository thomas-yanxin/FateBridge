# 六爻交节来源切换与缓存一致性

默认星历求出2026年节气并缓存后，同一进程设置`FATEBRIDGE_JPL_FILE=missing-liuyao-v19.eph`，新的原生计算会拒绝缺失的JPL文件，但旧程序仍返回同一个默认星历节气对象，连年月柱也直接复用。这是已复现的来源校验绕过，见修复前真实记录（本地数据：`validation/liuyao-v19-first-real-cache.json`）。在交节邻近，不同星历或时标的旧结果可能改变实际年月边界；单纯在返回字段中打印新来源不能修复它。

现在共同缓存键包含经校验的JPL选择、所选文件在搜索目录中的元数据，以及计算真正消费的已加载闰秒表内容散列。选择或替换文件、增删文件、重新加载不同闰秒政策后，节气及其依赖的四柱缓存会重新计算；恢复完全相同的环境仍可复用原缓存。严格JPL缺失、无效或不一致时保留既有结构化来源错误，所选JPL但原生库缺失时保留依赖错误。REST、MCP、CLI均验证相同边界及错误。

[Swiss原生源码](https://raw.githubusercontent.com/aloistr/swisseph/master/sweph.c)中的`swe_set_jpl_file`会关闭旧原生文件及行星位置状态；FateBridge已有逐次配置该文件的严格适配器。此次补齐的是它上层的Python节气缓存，避免缓存命中绕开该适配器。逐节气及整年前后均检查环境，观察到变化就丢弃不一致年，最多重试两次；这不能认证原生文件读取原子性或单次调用内未观察到的反复切换。

闰秒变化会影响TT根对应的UTC标签。回归在测试内存中构造明确标注为虚构的未来38秒偏移，用实际太阳求解验证TT根不变、UTC提前约1秒，及交节前0.5秒输入的年月柱随政策切换。它不改变生产[IERS表](../src/fatebridge/data/knowledge/western-leap-seconds.json)，也不宣称未来UTC已知。缓存必须识别已加载政策，不能用磁盘新文件的散列为仍在使用旧内存表的计算作担保。

另用实际有限DE441片段复核2000年小寒、大寒，复用已有DE440参考与原1秒门槛。片段不覆盖全年，合成来源切换用例也不认证实际天文精度。协议、首轮失败、字段勘误及样本分类见冻结资料说明（本地数据：`../tests/fixtures/liuyao_calendar_sources_v19/README.md`）。此前全时期Moshier的501个超差点仍保留；此次修复不改变太阳数值模型、历法参考答案或原典规则，不能以来源一致性替代精度或现实预测效力。

本轮固定源码、完整六爻回归、共享检查、两种星历环境交节对照及构建验收见第十九轮记录（本地数据：`validation/liuyao-depth-v19-verification.json`）。所有测试计数均为工程检查，仍未完成历法全范围、原典全书和自由模型解释认证，也未建立现实预测效力。
