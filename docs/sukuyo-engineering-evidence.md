# 宿曜工程取证的完整答复

当请求同时要求解释计算结果和验收依据时，分别交付结果与工程证据。领域结果中的 `reading_text` 解释该次计算，不包含仓库运行历史、全部测试回执或模型评审记录；仅转述该字段不能自动满足完整工程问题。

## 按问题绑定证据

保留完整题干，为每项实质要求登记实际证据文件、内容位置、字节指纹、所属快照和证据状态。计算视图保留全部科学字段，不能以生成的答文充当计算参考；工程附件另提供对应回执和完整相关子树。缺少所问证据时，明确指出缺项并补取，不从历史印象补造数值，也不通过缩写题干避开要求。

证据补充另存新版本，保留初始输入包及补充时间。首次答复前发现缺项与答复后的纠错分别记录；后续取得的证据不能倒填为先前角色已经读取。目录、影像读录、计算数据、实际运行和模型裁定分别归属。

离线工具 `fatebridge.validation.sukuyo_engineering.build_engineering_annex` 已可按显式工程请求组装附件。调用方提交逐字题干、计算文件的 `Artifact(path, sha256, source_version)`，以及每项 `Requirement` 的文件与 RFC6901 JSON 指针 `Selection`；空指针表示全文。每个文件只读一次并核对全部字节，所选子树完整复制，保留 null、不利行和未知。缺证据须给出明确原因，路径、哈希、指针、重复需求或同文件身份冲突均报错。它是本地工程辅助函数，尚未增加公开 MCP／REST／CLI 工程接口。

`binding_verified` 只表示这批字节绑定成功；`evidence_complete` 仅相对于调用方登记的需求，不证明需求表覆盖整题。`semantic_verdict` 与 `real_world_efficacy` 保持 `not_assessed`。该函数不识别自然语言路由、不生成答文、不复跑历史算法，也不认证版本声明的真实性。附件之后仍需完整答复和逐题语义复核，不能以附件校验替换旧验收。

完整工程答复可用 `build_engineering_response` 组装：在上述计算与证据之外，提交保存完整自然答文的 `Artifact`，其JSON含逐字相同的 `question` 和完整 `answer`；每项 `AnswerCoverage` 指向答文中一个或多个 `AnswerSpan(start, end, quote)`。位置单位是Unicode码点，左闭右开、从零开始；引用原文必须与该范围逐字相同。每个已登记需求恰好映射一次，重复、缺失、未知需求、空白片段、错误位置或引用漂移均报错。整答与所用计算／证据相同字节、完整解析对象相同，或所选证据子树直接等于整答对象时，均拒绝这种直接自引；这些检查不认证更广泛的来源独立性或排除全部改写与嵌套伪装。

组装结果保留完整答文、计算、全部相关证据子树和未取得状态。`literal_span_alignment_verified` 与 `declared_requirement_mapping_complete` 只验证字面位置和已登记需求的映射；同一段文字可对应多个要求，但这不证明其回答了这些要求。`question_requirement_completeness`、`source_support_of_answer`、`semantic_verdict` 和 `real_world_efficacy` 仍为 `not_assessed`。题干身份核对限于提交的问题与答文元数据；调用方仍须将请求文件绑定到原始题文和来源协议。完整答复另作语义复核，原生领域答文的既有失败不因此改标或与局部新答拼成新总分。

[离线入口脚本](../scripts/build_sukuyo_engineering_response.py)实际调用同一组装器。运行 `uv run --locked --extra dev python scripts/build_sukuyo_engineering_response.py --help` 查看参数。`--request`指定冻结请求JSON，同时须提供其`--request-sha256`和声明的`--request-version`；`--output`必须是尚不存在的文件。请求包含`request_kind: "engineering"`、完整`question`、`calculation`、逐项`requirements`、完整`answer`文件及`coverage`。每个文件描述为`path`、`sha256`、`source_version`；相对路径以请求文件所在目录解析。全部JSON先严格解析，非有限常量和指数溢出均拒绝；未知字段或字节漂移使执行停止。完整结果先序列化并写完临时文件，再以不覆盖已有路径的方式发布；写入失败不发布结果路径。结构与完整CLI调用见[可执行测试](../tests/test_sukuyo_engineering_response.py)。该入口不调用模型、不重算领域结果，不改变已连接MCP或共享计算接口。

## 完整问题的离线交付协调器

`scripts/sukuyo_delivery_workflow.py`提供`prepare`、`capture-generation`、`submit-review`、`finalize`四个离线入口，运行`--help`查看各阶段的显式路径、SHA和版本参数。它不调用模型；生成和整题裁定须由外部获授权角色真实执行。仅打印提示、装配文件或填写调用回执不能称为实际模型运行。

`prepare`的请求包含`protocol`交付定义的文件描述、具名`contexts`、覆盖全部case_id的`case_kinds`与`case_requirements`。交付定义分别绑定`original_protocol`、`scientific_protocol`及`required_contexts`清单；原协议和新科学协议的全部ID、逐字题文、题序及`review_standard`须相同。科学协议每项还须有`view_file`、`view_sha256`；`view_encoding=gzip_utf8_json`还须提供`decompressed_view_sha256`。协议、全部科学文件与全部可用上下文先实际读验，再形成输入；不只转交路径，也不剥离未知、不利分支、嵌套summary或未来科学字段。

上下文描述使用`name`、`artifact`及可选RFC6901 `pointer`，须与必需清单的名称、文件身份和选取位置逐项一致。两份协议的`common_source_context`还须被清单完整覆盖，不能仅修改清单便删掉原协议的共同上下文。明确缺项时使用`unavailable_reason`而不同时提供文件，产物保留预期文件身份和选取位置；这不是缺项无关紧要的证明。domain、engineering、uncertain及需求表均由调用者登记，不是自动路由或完整性证明。普通领域题不为复用附件函数而虚标工程题；需求表遗漏的原题义务仍须回答和审查。

完整JSON值采用带标签的对象／列表及共享引用保存，`expand_prepared`递归验证引用、指纹、无环与完整值指纹后展开；原数据中形似ref、dict的对象仍按数据保留。它保存解码后的JSON值，不声称重建压缩文件或原JSON排版；原始压缩／解压字节指纹、大小与文件路径另留。成功准备的状态是`prepared_not_generated`，不是生成或解释验收通过。

生成角色须接收该输入，逐题给出完整首答；首答JSON包含对应的`prepared_input_sha256`与完整`answers`，逐项含原`case_id`、逐字`question`、完整`answer`。`capture-generation`核对全部ID、顺序、题文和输入身份；不接受少题、改题或用旧答文件替换输入。外部执行回执须绑定`input_sha256`与`output_sha256`，但这些字段只验证声明的一致性，不认证调用真实性、先前阅读、首次调用或可信时间戳。控制者仍须保存实际角色记录、原始首输出及反馈暴露，不能挑多次运行的最好答案。

`submit-review`复用完整问答绑定器，形成保留完整输入和首答的复核包。复核角色须审全部原题、完整答文和必要证据，不限于需求表或覆盖片段。评审JSON绑定`review_input_sha256`，并按原顺序给出全部`reviews`；每题显式提供`verdict`及`material_errors`、`important_omissions`、`unassessed_material_claims`三个数组。少题、缺数组、输入互换、带实质问题却判pass均停止，不能把缺字段默认成零。

`finalize`重新核对准备、首答、复核及其依赖后汇总外部声明。`all_whole_answers_passed_declared_review`只表示完整外部裁定数组的结果；`semantic_judgments_independently_verified`、`external_execution_authenticated`仍为false，原native门、来源独立性与现实效力保持各自未评状态。工具不能机械判断答文的实质真假。

来源或答文漂移须另存新准备／尝试并披露补证或修订关系，不改旧文件、不倒填首答所见。原路径与字节须继续可用，才能重新核验阶段依赖。所有输出采用完成临时写入后排他发布，已有路径不覆盖；它不构成跨文件数据库事务或父目录掉电持久性保证。工程附件及逐项字面覆盖组装器继续单独可用，其机械布尔值不替代完整问题的语义裁定。

新整题交付路径与既有原生领域渲染分别报告。完整180题经过新路径，也不能改名为旧native180全门通过；旧首答、首次裁定、原分母与全部失败保持。

## 解释数值的对象

整题语义复核包可用 `fatebridge.validation.sukuyo_semantic_packet.build_whole_answer_review_packet` 组装。输入为分别带路径、SHA-256和版本声明的完整请求与完整答文JSON文件；请求的 `cases` 含 `id` 与完整 `question`，答文的 `answers` 含对应 `id` 与完整 `answer`，也可显式选择 `case_id`。逐题ID必须唯一，两个集合完全相同；已有答文问题字段须与请求逐字一致，缺题、多题、重复ID、空题／答文和文件漂移均停止。

复核包同时保留两份文件的完整UTF-8原文、实际字节数、完整解析值及全部元数据，按请求顺序交付逐字答文和答文字节指纹。题数从实际题目数组导出，与不同问题文本数分列；输入自报的题数原样保留，不当作实核题数。原字节与解析值来自同一次读取，不能用答文自报、另一个来源文件的长度或后来混排数量替原输入作证。此绑定只说明本次所读文件，不独立证明早先生成者实际读过它们、文件原始形成时间、来源独立性或语义正确。

[离线复核包脚本](../scripts/build_sukuyo_semantic_review.py)调用同一函数，须显式提交两份文件的指纹与版本，输出路径不得已存在。该脚本不调用模型、不改写原答、不产生通过分数；`semantic_verdict`、`source_support_of_answer`、`source_independence`、`original_gate_verdict`及`real_world_efficacy`均保持 `not_assessed`。原协议、完整科学视图及相应上下文仍须实际提供和审读，包内路径引用不表示所指文件已被该函数读验。补证包另存新版本，保留原首评和未核范围。

每个工程计数同时说明它数的是什么、来自哪个版本、如何取得以及能证明到哪一层。案例、原像区间、端点出现次数、不同端点值、条件组合、文本表槽、印刷记录行和完整答题数采用各自单位；重复字段或同源副本不能计为新的独立观察。

源清单的成员数与作者改动路径、并行改动路径分别交付。选定源码相同不能扩成完整运行依赖图相同；历史执行回执不能扩成当前工作区重跑。实际进程、运行版本和执行时序应有回执，普通请求中只作的数值转换诊断不能被描述为已经执行外部运行时。

## 先完整解释计算，再说明验收边界

逐人保留时刻已知状态、输入及解析后的时区、全部参考日期、历法分支、宿名与候选。双向关系、日期条件、共同重建支持和原无约束组合按实际返回交付；不存在的支持字段不补造。区间长短不用于排序、删行或解释出生概率。

工程附件回应题目实际询问的来源、原判据、执行范围、失败和未定项。局部修订的复核结果单独报告，不能将旧题的修订结果拼接成未经完整重跑的新总分；新增通过子集也不能覆盖旧失败或缺失的评分字段。

馆方对版次、装订和年款的说明可以增强目录层证据，但不能代替影像原字裁定或物理鉴定。古代平明、原典半日与闰小月交叠规则未建立时，保持其条件状态。工程测试、来源一致和解释忠实分别验收；现实预测须另有事前登记及真实结局。

定位卷页时按[连续正文与不同卷次](sukuyo-source-alignment.md)分别核实物题名、电子juan开闭和登记库范围。空索引须保留查询边界及正控制，不能当作全世界没有目标；局部文本相合也不自动认证具体底本或历法规则。

## 来源查重先于新增证据计数

新来源采用前，冻结旧证据及所选资料文件的路径、字节指纹和候选URI／SHA。运行 `scripts/check_sukuyo_source_novelty.py --baseline <冻结清单> --candidates <候选列表> --report <核对结果>`，把链接曾被引用、字节指纹已经记录和原制品直接相同分开。相同材料的多个命中不是多个见证；不同SHA也不自动成为独立传本。

同一目录对象再次取图前，先核已有具名私有原件、manifest及取得回执。按目录ID、画布ID、原URI、尺寸层级和实际SHA分别绑定；已保存的缩图、原尺寸图与局部读录分别记账。有限公开／源码基线未匹配时，仍须检查已知的相关私有缓存，不能据此宣布全项目首次取得。旧原件恢复与本轮网络首采分列，后来的恢复不回写首轮成功／失败数；重复曝光、相同文件和同名著录不能增加独立见证票数。
评审汇总须按字段分别交付重要遗漏与未核定实质断言。缺规范数组造成的null保留在对应总数，不能抹掉已经明确的遗漏数；显式字段别名规范也不改写原始机械失败或原模型输出。修订说明绑定实际字段和值，不能仅用后续正确的总分抵销首答中的错误。



该工具完整核验声明基线文件的字节，文本搜索不展开ZIP等二进制内容，也不解析URI别名。`not_found_in_this_text_baseline`只表示在此范围未匹配，不能改写成首次发现、独立观察或规则已接受；观察数量保持未知，工具不授权历法或原典改动。基线漂移或缺文件须停止，不能静默丢行后报通过。

基线可用 `text_encodings` 为已列出的文本文件显式声明受支持的编码，例如官方HTML所载EUC-JP或Shift_JIS；未声明时仍严格按UTF-8读取。原字节先完整核哈希，再严格解码，实际编码与声明状态列在 `text_decoding`。不自动猜编码、不忽略或替换坏字节、不因此展开二进制档案；声明无效或解码失败使整次核验停止。解码成功也不认证声明为真，更不解决URI别名、语义等价或传本独立性。补充编码元数据须另存新基线，保留首次失败及全部原成员。

目录识别、片段字形、理论天体位置、月日配宿和现实结局仍分别验收。勘文所记本命宿与月球宿度，即使相同，也不独立证明它采用当前27宿月日算法；选定日界前须证明两者方法身份相同。档案日期和预测内容也不能代替独立结局或现代前瞻登记。

## 宿占整盘的语义核验

`semantic_calculation_view("suzhan", result)`是既有的历日宿曜视图，仅保留params、sukuyo及rulesets；不得把该视图的验收称为完整星图解释通过。需要说明宿占整盘时，使用`complete_suzhan_calculation_view(result)`：保留实际返回的input_normalized、chart、astronomy、validation及所有其他非展示字段，包括未来字段、失败、未知、完整候选和未计算状态。

完整视图只剥离既定顶层展示／运行包装和递归reading_text，不删除嵌套的科学summary。必需分支缺失须报错；astronomy明确为null时保持null，不把已有行星坐标等同已计算二十八宿。副本编辑不改变原始结果。视图完整只证明证据未因投影而丢失，不证明数值、古代宿界、历名、方法身份或预测效力。

历日27宿、现代不等宽研究宿位和旧黄道等分示意分别解释，按实际method、coordinate_frame、accuracy及backend字段负责。历史文书可同时引用诸曜行度、宫位和宿名；不能由同名或前日相合把它并入当前月日算法。原历日视图、原180题、旧缺字段及不利首评继续单列，不以整盘补充题覆盖。

## 原典数词和定义位次
