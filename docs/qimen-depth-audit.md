### 规则、解释与接入

公开输出新增 `ju_method/ju_term/calendar_policy/rulesets/rule_profiles/rule_trace/structure/patterns/source_disagreements/assessment`。宫内新增方位、五行、寄干、寄星及 `evidence`。已覆盖门迫与宫克门的区分、时旬空支、九星旺衰、六仪刑宫、卷二王璋口径的三奇入墓、部分明确干加干格、星门分别伏吟反吟及同阴阳时干克日干的五不遇。

这些条件命中只给出传统含义，不生成现实事件概率。天遁、地遁、人遁、神遁的明确组合，三奇得使及玉女守门，并返回附加条件和冲突。该书还包含本命行年、三遁其他异文和大量未实现规则；没有全部自动判定用神、旺衰综合权重和精确应期。规则须逐条绑定原典依据；软件派生结果或知识条目名称不构成原典认证。

同一领域服务用于 REST、原生 MCP 与 CLI；新增三端实际调用测试，同时检查结构化结果、快照、导出及不支持选项的失败语义。咨询读取规范位于 [奇门证据分支](interpretation/zhanbu/qimen-evidence.md)。程序证据一致性不能替代真实模型的行为验收。

示例（钟表时，置闰；显式提供经度后也可选择真太阳时）：

```bash
uv run --locked --extra dev fatebridge qimen \
  --analysis-year 2026 --analysis-month 1 --analysis-day 19 \
  --analysis-hour 23 --analysis-timezone Asia/Hong_Kong \
  --no-use-true-solar-time --qimen-options '{"ju_method":"zhirun"}' \
  --strict-fields --no-include-snapshot-text \
  --fields qimen.ju_text qimen.calendar_policy qimen.stem_context qimen.rulesets qimen.zhifu qimen.zhishi qimen.palaces qimen.patterns qimen.source_disagreements qimen.assessment
```

拆补用 `{"ju_method":"chaibu"}`；只支持 `layout=direct`。日旬字段改变及中宫 `null` 是有意的纠错，消费者需要处理寄宫数组，不能依赖旧“中门”。

补入卷二“三诈五假”中的三条完整命名句。影印第25—26页（810-945至810-946）及标注保存在 `tests/fixtures/qimen_classical_v13/`。真诈为三奇合开休生门临太阴，重诈临九地，休诈临六合。实现明确采用现行时家转盘的天盘奇（含寄干）、实际八门和所选八神同宫这一层映射，不将该实现约定说成已经独立验明全书盘层。每宫增加 `evidence.three_deceptions`，正式名称进入 `patterns`；上下文与完整格局均可沿本次 `rule_trace` 追溯。

歌诀及释文“得二亦吉”与正文“门合太阴而无三奇，犯者不利”并列保留。程序只给出要素是否存在、完整名称是否命中和缺项类别，不对缺项自动判吉凶，也不把原文十分、七分变成成功概率。这个新暴露的适用／优先问题作为第8项未通过加入原典审计，原有7项不删除。五假未由本规则实现，三条命名句不是三张独立完整古例盘。

丁、休门、太阴同宫时，既满足人遁又属于真诈，格局证据用 `overlapping_evidence_group` 标明共享事实，不作两份独立印证；其他真诈不因此被叫作人遁。具名三诈仍与同宫门迫、入墓等证据并列，不能覆盖限制或自动称为全盘吉。一次源代码检查中的“两奇同宫”假设已撤回：遍历现行1080个声明盘，没有这种寄宫实例；双奇只作为合成防重复测试，不冒充实盘。实际寄奇重诈见阳六局丙寅时艮宫天盘癸寄乙、开门、九地，这是按现行规则推导的例盘，不是新增影印古例或现实结果。

## 时间与历法

### 物理时刻与真太阳时标签

纽约2026-03-08 02:30不存在，2026-11-01 01:30有两次。此前直接时间路径没有调用夏令时检查，能返回一个未经消歧的盘。现在奇门专用入口与三式合一入口均验证原始民用钟时，两种模式一致拒绝上述输入；明确的 `-04:00` 与 `-05:00` 可分别表示重复区间的两个真实时刻。

检查只针对原始输入。纽约2026-03-08 03:30配经度-74.006是真实有效的时刻，真太阳时校正后约为02:23；这个02:23是太阳时标签，不是当地不存在的民用02:23，必须保留有效。回归同时检验专用奇门与三式盘面一致。

每个HKO节气按发布分钟前后各2分钟，在香港、纽约以及两种钟时模式下检验拆补法取节气，共576次；结果由实际民用交节时刻决定，不能随经度校正提前或推迟。它验证现代定气和已列时区范围，不证明古代平气历或所有历史时区均正确。

继续核对发现，旧的 `dateutil.tzfile` 读取结果在纽约、柏林2038年后的夏季缺少1小时夏令时；1900年纽约、柏林、悉尼则错误沿用已废除的地方时。例如纽约2040-07-01 01:30、经度-74.006°，真太阳时应约00:30，旧读取器却约01:30，时辰从子误成丑。纽约1900-07-01 01:01还会因旧地方时偏移跨过01:00边界。这些是确定时间转换错误，不涉及预测效度。

现在按[Python ZoneInfo文档](https://docs.python.org/3/library/zoneinfo.html)读取锁定依赖内的IANA TZif，避免操作系统数据库不同造成规则漂移。[IANA北美](https://data.iana.org/time-zones/tzdb/northamerica)、[欧洲](https://data.iana.org/time-zones/tzdb/europe)和[澳洲](https://data.iana.org/time-zones/tzdb/australasia)的Zone/Rule原文用于人工推导15个UTC偏移、夏令时参考及6个2040年跳时、重复时刻。原文摘录、行号与指纹保存在 `tests/fixtures/qimen_timezone_iana_v1/`。当前锁定pytz 2026.5 / IANA 2026e，结果的 `calendar_policy.timezone_rules` 公布实际版本与 TZif 来源名称；文件指纹由内部资料维护；明确固定偏移单独标记。未来日期遵循所冻结规则的外推，不能保证未来法规不变，IANA历史条目也未逐个地点实地考证。

### 等价时刻、明确偏移与夏令时边界

复现输入为 `2026-09-06 01:30`、`America/Santiago`、经度−70.6693、启用真太阳时。该输入与 `2026-09-06 04:30+00:00` 指向同一实际时刻；修正前三式前者得到太阳标签9月5日23:48、癸未日壬子时，后者却得到22:48、壬午日辛亥时。问题位于共享起盘种子：修正量按目标时区计算，却加在原始ISO偏移钟表上，换区跨过夏令时转换后多出一小时变化。现在先将输入转换为指定时区，去掉时区标签后做太阳时钟表修正，原民用时刻继续负责交节，太阳标签负责日时层。两种输入现在得到同盘。秒数原本已保留，该范围未将不存在的“丢秒”问题算作修复。

另一问题是明确写成 `2026-11-01 01:30-04:00` 或 `01:30-05:00`、目标区仍写纽约时，两个已确定的实际时刻都会被原来的重复钟时检查拒绝。现在ISO偏移输入保留其实际时刻；未带偏移的本地重复或不存在钟时仍拒绝。纽约两个时刻在该经度的太阳时分别落子、丑，均与专用奇门的相同显式偏移输入相符。Python官方文档区分[保持实际时刻的时区转换与只替换时区标签的操作](https://docs.python.org/3/library/datetime.html#datetime.datetime.astimezone)，本修复遵守这个区分；太阳标签本身不是再次移动后的民用实际时刻。

新增回归夹具（本地数据：`../tests/fixtures/qimen-clock-representations-v1.json`）包含8组日期／时区案例；直接时间／太阳时、拆补／置闰共32组等价时刻对照。它们是发现问题后的回归与表示不变性检查，分别计数，不增加75个独立历法参考数。新增[测试](../tests/qimen/test_qimen_offset_clock.py)还比较专用奇门与三式实际盘面、明确偏移的重复小时，以及真实REST／原生MCP／CLI交付。原典规则版本仍为2.8.0；该范围修改计算实现，冻结研究通过整个包的实现指纹区分版本，没有改写旧研究的预测或结果。

### 真太阳时修正依据与边界可辨识性

当前共享计算在该范围开始前已经使用 Swiss Ephemeris `time_equ` 按实际UTC时刻求均时差；该范围没有把既有升级再算作一次算法修复。依据[Swiss程序说明9.4](https://www.astro.com/swisseph/swephprg.htm)，均时差为视太阳时减平太阳时，入参为UT、返回单位为日。现行实现以UTC近似UT1，未接入实测DUT1。原奇门只给总修正量，未完整保留分项和方法，难以判断日时标签来自何种修正；该范围补齐种子计算时的依据记录，不在输出阶段重算或根据总量猜方法。

新增 `calendar_policy.solar_time_adjustment` 保留原实际UTC时刻、经度差、均时差、夏令时、总量、算法标识、UTC近似UT1及修正后的太阳钟表标签，并验证各项相加与真实标签改变量一致。该标签供日时层取用，交节继续沿用原物理时刻。直接钟表时明确未应用；自备种子没有分项记录则标记缺少依据，不伪造算法。快照和整条引用保留精度限定；标签距最近时辰／23点换日的秒数只是几何距离，不是统计置信区间、实际误差界或认证结论。

先固定12个边界及钟时回拨回归时刻，再请求[NASA/JPL Horizons视太阳钟与DUT1](https://ssd.jpl.nasa.gov/horizons/manual.html)。原始响应、请求参数、选择协议和指纹保存在 `tests/fixtures/qimen_solar_jpl_v1/`。直接解析原表期待值，未由Swiss或当前奇门输出产生；其中包含其他术数已研究的重复时刻，12个有限参考不当成12项全新独立证据，更不是现实事件预测。未来日期采用该响应披露的地球自转参数预测或保持末值，也不是未来观测。

12个太阳钟与当前计算均在事先固定的5秒核对容差内，最大标签差约0.664秒；这里的5秒只描述参考核对，不是所有日期、经度、输入时刻或真实测量的误差保证。2026-02-15 23:14 UTC、经度0的当前太阳标签为22:59:57.157，距23点约2.843秒；JPL名义太阳钟约22:59:57.405，同样在换日前，但参考±5秒覆盖换日两侧。因此这例的名义匹配不能认证日时归属，台账保留 `classification_verifiable_at_reference_tolerance=false`，不删难例或放宽容差。其余标签的日干支期望从既有HKO甲午日锚点按日期差推导，另记为派生，不冒充新增逐日发布的干支观察。

历法报告区分参考数值一致与边界部分未认证；注入数值不符合时必须返回失败，不能被部分状态覆盖。所选古典规则仍为2.12.0，该范围不改变排盘数值、五假等传统映射或既有9项原典未通过。真实前瞻样本仍0，结构化修正依据与参考一致不能认证任意模型解释或现实预测。

## 盘面与原典条件

### 盘面结构与计算规则
