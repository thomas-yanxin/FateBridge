# 风水输入类型与历法事实

数值和日期须按已发布字段类型提交。`true` 不能代替1度、第一运或零误差，年份不能填入时刻字段，Unix时间戳也不能冒充出生日期。类型错误在排盘前拒绝，避免生成形式完整却使用错误事实的星盘。

本说明由FateBridge维护，文档修订1.0（2026-10-22），属于工程输入合同。它不增加任何古典规则或现实预测效度；原有计算规则集版本不变，实际源码与安装包身份由验收散列记录。

## 输入方式

| 字段 | 正确形式 | 拒绝的形式 |
| --- | --- | --- |
| 角度、误差半径、距离、经纬度 | JSON数值，如 `22.5`、`0` | 布尔值、数字字符串、NaN、无穷值 |
| 有效年、运数、节月、楼层、辈分 | 范围内整数，如 `2026`、`8` | 布尔值、数字字符串、非整数 |
| `birth_date`、地磁参考日期 | `YYYY-MM-DD`；Python调用可传 `date` | 时间戳、带钟时的字符串或 `datetime` 对象 |
| `query_at`、`birth_at`、`event_at` | 明确日期和钟时的ISO字符串；Python调用可传 `datetime` | 数字时间戳、数字字符串、只有日期而没有钟时的输入 |

原有取值范围、互斥输入、时区、夏令时和历法边界检查继续适用。时刻所需时区按对应工具的公开合同提供，不从年份或只有日期的输入补出钟时。

JSON Schema将 `8` 与 `8.0` 视作同一个整数值，因此允许范围内的 `8.0`，只在精确相等时归一为整数；不舍入 `8.5` 或具有非零小数部分的Decimal／Fraction。数值字符串 `"8"` 仍为字符串。这遵循[JSON Schema数值规范](https://json-schema.org/understanding-json-schema/reference/numeric)。

以下为虚构的合同示例，显式确认有效年与节月；不代表实际时刻的历法核验：

```json
{
  "effective_solar_year": 2026.0,
  "solar_month_number": 8.0
}
```

## 修复依据与验证

此前可复现的错误包括 `bearing_degrees=false` 被当作0度、宅向 `true` 被当作1度、旧玄空误差 `false` 被当作零误差、宅运 `true` 被当作第一运。`query_at=2026` 或 `"2026"` 曾被转为1970年初的时刻，进而排出1969有效年盘；数字出生日期也曾被按Unix时间解释。这与公开字段的数值或日期合同不一致。[Pydantic转换表](https://docs.pydantic.dev/latest/concepts/conversion_table/)说明了这些宽松转换的来源；它们不能代替用户已确认的测量及历法事实。

输入模型统一在原字段约束前检查事实类型，嵌套模型和MCP展平字段保留同一检查。当前45个风水输入模型中31个数值／日期字段逐项核对，八工具原有输入／输出及必要字段Schema保持不变。正例额外覆盖每个字段的范围内有效值，再用同值数字字符串核对拒绝行为，避免只因越界而误判类型保护有效。

完整复现、原始失败、冻结源码、安装包及三端结果见第十九轮证据（本地数据：`validation/fengshui-input-types-v19-evidence.json`）。这些检查验证类型、计算输入与接口一致性，现实前瞻案例仍为零。
