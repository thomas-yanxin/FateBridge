# 周期参考时刻的小数小时与小数分钟

[人类图说明](human-design.md) · [调用合同](contracts/human_design.json) · 本轮验收记录（本地数据：`validation/human-design-reference-fraction-verification.json`）

本次修复`cycle_reference_datetime`把时间的小数一律当作小数秒的问题。输入`1980-09-09T12.5Z`原来被读为12:00:00.5，修复后为12:30；`12:15.5Z`原来被读为12:15:00.5，修复后为12:15:30。出生12:15而参考12.5的合法输入曾被误拒为早于出生，原始完整错误结果保留，没有删除或改写。

## 来源与范围

[ISO 8601-1:2019/Amd.1:2022第5.3.1.4条](https://cdn.standards.iteh.ai/samples/81801/f527872a9fe34281ae3a4af8e730f3f8/ISO-8601-1-2019-Amd-1-2022.pdf)说明小数跟随最低已给出的小时、分钟或秒单位，且省略更低单位。[美国政府保存的ISO日期时间格式原文](https://www.govinfo.gov/content/pkg/GOVPUB-C13-51807c97cccd94fff3df87fce4c9838b/pdf/GOVPUB-C13-51807c97cccd94fff3df87fce4c9838b.pdf)也列有小数小时、分钟及基本／扩展写法。[Python文档](https://docs.python.org/3/library/datetime.html#datetime.datetime.fromisoformat)明确将小数小时和小数分钟列为不支持项；其实际解析器仍接受部分这种字符串，却把小数当作秒。接口原来声称接受带时区ISO时刻，不能将这种误解静默传入计算。

新增领域内的解析函数先保留原解析器的日期、周日期、分隔符、明确偏移和缺时区行为，再对当地时间中的小时／分钟小数按整数微秒展开。小时按3600秒、分钟按60秒展开为标称民用钟字段，随后仍走原有时区、UTC／历史UT1、TT转换及闰秒政策。小数最多6位的原限制保留；没有静默截断或引入新的舍入。Python3.10不能直接解析的已识别表示先转换成完整日历／时分秒形式，并由标准日期、周日期和时区范围检查核对；无效日期和小时不会被修复成合法值。完整秒小数和之前修复的亚秒偏移保持原语义。缺时区仍拒绝，不推测当前时刻或地点。

这是已有入口的定点修复，不是通用ISO 8601实现。原有偏移解析兼容范围继续保留；不声称所有ISO扩展格式均受支持，也没有引入用小数小时／分钟替代闰秒60秒标签的新记法。原有完整的正闰秒标签仍按冻结IERS记录确认。

## 完整解释与输入顺序

生产入口、请求预检和完整解释重放使用相同的确定性展开规则，独立参考另由无FateBridge导入的整数历法生成器建立，避免仅以同一实现自证正确。展开后的UTC标签和TT绑定到实际转换记录与有理数先后轴；天文计算仍使用原有双精度TT，不宣称微秒级天文精度。

完整解释重放还修复了只看字符串第17至19位是否为“60”的闰秒识别。合法输入`12.123600Z`中的数字碰巧占据这两个位置，原来会误入闰秒分支；现在只对完整匹配既有闰秒格式的标签进入该分支。这不增加或取消任何已公布闰秒日期。原先未能核验的完整结果和误通过的错误参考时刻均保留；修复后的核验会拒绝旧错误时刻，即使其原业务散列仍一致。

出生TT、人格／设计激活、88度太阳弧求根、原有周期交会搜索和固定教学顺序不因参考字符串展开而改变。只允许参考标签、参考TT、相应转换记录、输入先后依据及相对该参考时刻的说明发生因果变化；不按年龄或新时间分配传统第六线阶段。与明确展开的完整秒输入比较时，除原始输入回显与执行回执外，完整业务结果必须逐值一致。
