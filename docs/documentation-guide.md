# 文档写作与维护

[文档中心](README.md) · [贡献指南](../CONTRIBUTING.md) · [开发检查](development-guide.md#文档维护与验证)

文档要让读者完成一件事：运行计算、接入接口、查到约定，或理解实现选择。先确定读者和任务，再决定内容放在哪里。修正文档可以直接提交 PR，无需先改代码。

## 内容放在哪里

按 [Diátaxis](https://diataxis.fr/) 区分入门、操作、参考和解释，保留现有文件路径，避免为分类而搬动所有页面。

| 读者需要 | 所属页面 | 应包含什么 |
| --- | --- | --- |
| 判断项目是否适合自己 | 中英文 README | 定位、能力范围、最小体验与后续入口 |
| 完成第一次计算 | [快速入门](getting-started.md) | 安装、一个虚构请求、成功结果与下一步 |
| 完成一项操作 | 接入、部署、星历、故障排除指南 | 前提、按顺序执行的步骤、成功判据与恢复办法 |
| 查询准确约定 | [运行配置](configuration.md)、[API 参考](api-reference.md)、[生成合同](contracts/README.md) | 字段、默认值、范围、错误及协议差异 |
| 理解为什么这样计算 | 核心概念、架构、领域专题 | 方法、例子、来源、实现选择及已知限制 |
| 贡献与验证修改 | 贡献、开发、脚本和测试指南 | 修改入口、检查命令、覆盖范围及分发要求 |
| 核对结果解读 | `docs/interpretation/` | 按需查阅字段读取、来源与方法范围 |

一页可以有多个章节，但开头应回答它解决什么问题。长专题先给常用任务和目录，再展开公式、来源与验证；不要要求新读者先读完研究记录才能调用工具。

## 同一约定只维护一份正文

其他页面可以给最小例子或一句提醒，并链接到负责维护该约定的页面。机器合同优先从实际实现生成，避免手抄 Schema。

| 内容 | 核对的实现或来源 | 文档位置 |
| --- | --- | --- |
| 安装、版本和入口 | `pyproject.toml`、`__init__.py`、入口模块 | 快速入门；README 保留最小命令 |
| 环境变量与加载顺序 | `utils/runtime.py`、`.env.example`、各变量读取处 | 运行配置；安全边界见 `SECURITY.md` |
| 工具名称、字段与协议差异 | `services/catalog/`、请求／响应模型、实际发现记录 | API 参考、生成合同；覆盖矩阵维护实现范围 |
| 操作示例与完整结果读取 | 实际 CLI、REST、MCP 调用 | Agent 接入指南、示例目录 |
| 计算方法、来源和未决项 | 领域实现、规则数据、独立参考 | 对应领域专题；算法状态汇总当前限制 |
| 模块与依赖方向 | 实际导入、绑定和执行代码 | 架构说明 |
| CI、构建与发布 | `.github/workflows/`、打包声明 | 开发指南 |

中文与英文 README 的能力、安装步骤和限制应一致；不要求把全部专题复制成英文。生成文件的源和检查命令见[开发指南](development-guide.md#文档维护与验证)。

## 写清楚，而不是写工作汇报

- 用当前行为作主语。例如“重复钟时必须提供已确认的 UTC 偏移”，不写“本轮进一步补齐时钟处理闭环”。必要的版本差异放到升级说明或 CHANGELOG。
- 一段解释一个问题。先写结论或操作，再写原因和条件；并列字段用表格，操作顺序用编号列表。避免把十几个字段和多次修复挤进一句话。
- 说明术语的实际含义。首次出现 `partial` 时说明它限制哪一层；说明“字段投影”是选择返回字段，“run”是一次计算。字段名和原典术语保留准确拼写。
- 删除“进一步完善”“全面赋能”等无法核对的措辞。把“已完成”“支持”“精确”限定到实际方法、输入范围和证据，不用测试数或工具数证明完整性。
- 交叉引用使用有意义的链接文字。不要写没有入口的“见第十二轮验收”“见本次核对”，也不要只给一个无法定位的“详见相关文档”。
- 一般限制在所属概念或专题解释一次，在确实影响操作处简短提醒。保留反例、失败、来源分歧和未知；精简表达不能改变其含义。

## 示例、来源与历史记录

可执行示例注明运行目录、安装方式和必要服务，使用虚构资料，并给出预期字段或退出状态。占位符写明替换方式；不要把一台开发机的绝对路径、临时文件或已登录账号作为默认前提。源码命令使用 `uv run --locked --extra dev`。

来源应能定位到作者、版本、页面或固定提交。未随 Git 分发的资料标明本地数据路径及取得方法，不创建指向缺失文件的仓库链接。公开结果中的来源信息、私有存储校验和研究材料的文件散列各有不同用途，按当前合同描述。

指南维护现行行为。逐轮日志、耗时、工作区变化和单次测试数量放在仓库外的验收档案；正文只保留理解当前范围所需的结论。迁出历史记录前保存原文并校验字节，不丢弃失败或将后续复验写成原批次全绿。清理方式见[仓库维护](repository-maintenance.md)。

## 提交前审阅

从一个不熟悉项目的读者角度确认：能从文档中心找到这页，知道前提，复制命令取得所述结果，理解结果的范围，并找到出错后的下一步。删除标题时搜索全部引用；重组长文时保留仍被使用的锚点或同步所有调用方。

按[检查命令与覆盖范围](development-guide.md#检查命令与覆盖范围)运行链接、示例和生成物检查。自动检查可以发现断链和合同漂移；语言是否清楚、来源是否支持结论，仍需逐页审阅。
