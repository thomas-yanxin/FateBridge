# 八字节气来源失效审计

本次修复解决精确节气求解不可用时仍返回成功排盘的问题。四柱、起运、流年、流月及附带节气窗口必须检查实际使用的节气来源；`linear_1900_fallback` 和 `unknown` 均不能作为已计算的天文交气边界。正常求解路径、原有出生年份范围和纯干支算术保持原口径。

## 已复现的问题

故障注入将 `_solar_term_utc_via_swe` 的返回值置为 `None`，关闭真太阳时并清理节气、四柱及派生缓存。2026-02-04 07:09，UTC+08 的同一输入，在修复前两次均返回 HTTP 200，但数值求解路径给出丙午年、庚寅月，线性回退路径给出乙巳年、己丑月。该环境的两个立春边界分别为 04:02:07.926618 和 10:16:32.812200，相差约六小时十四分钟。

这是提供者故障回归，不能当作新的独立天文测量。数值路径的秒及小数秒也不代表独立认证的物理精度。[香港天文台](https://www.hko.gov.hk/tc/gts/time/24solarterms.htm)定义节气为太阳黄经每隔十五度的边界；[日本国立天文台2026年历要项](https://eco.mtk.nao.ac.jp/koyomi/yoko/2026/rekiyou262.html)给出的立春是日本标准时2月4日05:02，即UTC+08的04:02。这只能作这一已知例的分钟资料核对。

## 修复与验证口径

`require_calculated_solar_term` 检查被实际使用的对象，不能以另一年份或另一份缓存的提供者状态替代。检查覆盖年界立春、月界的前后两个节、综合历法上下文的相邻节气、流月时间轴及二十四节气时间轴。相关直接领域计算共用这些入口，精确求解不可用时返回标准 `dependency_missing` 错误。无具体时刻的干支年份换算及独立日柱算术不依赖这个检查。

`swisseph` 在这里表示数值求解库可用，不认证其精度，也不表示每次必定使用某一Swiss星历数据文件；该库还可能使用Moshier内置模型。TT与UT的区别遵循[Swiss Ephemeris官方接口文档](https://www.astro.com/swisseph-download/doc/swephprg.2.10.htm)，历史与未来民用时标换算仍须分别验证。通用的低精度节气辅助函数仍可能返回线性值，不能据此宣称整个产品已消除所有回退；本次门槛针对八字的实际计算及输出依赖。

测试同时覆盖八字综合、九专题和七个时运工具的REST、原生MCP、CLI；并单独改变一个实际边界的来源，确认其余节气可用时仍会拒绝被污染的边界。人工合成时间只测试序列化或时区算术，明确隔离来源检查，不给合成数据伪造Swiss来源。

## 验收状态

独立实现、官方表一致性、工程回归、原典判定是不同证据。本次故障拒绝不计入天文正确率，不改变原典旺衰不符的记录，也不证明现实预测。当前完整目标仍为未证实；最新运行记录见三项目标要求（本地数据：`validation/bazi-three-axis-requirements.json`）及本地验证记录（本地数据：`validation/bazi-classical-routes-local-verification.json`）。

第二十三轮增加独立命名的[解析太阳模型](liuyao-v23-solar-model.md)。`swisseph`不再是已计算交气的唯一提供者标签；已识别的新解析模型按其真实模型名与系数来源消费，原线性/未知来源拒绝继续生效。严格JPL与显式解析配置冲突也拒绝，不把原生求解失败包装成成功。TT有限域比较、历史民用时标及现实预测仍分别验收。
